# Iumrah Business: защита Flight Sync от обнуления — 15.10.2026

## Диагноз

Раздел «Авиабилеты → Опубликованные» хранит/запрашивает список в Package Engine (`/api/admin/package/flights/curated`). Публичная `/flights-feed/<stable-id>` не читает эти записи непосредственно: она возвращает последний сохранённый снимок из таблицы D1 `business_flight_sync_feeds`. В исходном коде приложение сохраняло текущее SwiftUI-состояние `published` без контрольного чтения; Worker принимал даже `flights: []` и полностью перезаписывал сохранённый снимок. Поэтому 57 рейсов могли отображаться в Business при пустом внешнем feed. Это вывод по коду и присланным скриншотам, а не заявление о содержимом действующей БД.

## Исправлено

- Клиент непосредственно перед **каждой** записью снимка заново запрашивает авторизованный `/api/admin/package/flights/curated`, исключает истёкшие записи и **не отправляет пустую выборку**. Ошибка чтения не затрагивает предыдущий снимок.
- Повторная синхронизация запускается при открытии экрана и возврате приложения из фона, даже если локальный массив не изменился. Предусмотрена также прежняя автоматическая синхронизация при публикации/удалении и ручная кнопка.
- На карточке Sync показаны отдельно «В Business: N» и «Feed: M», вместо ложного сообщения «доступ включён — N рейсов» без проверки зеркала. Ошибки автообновления теперь видны.
- Worker возвращает `409 FLIGHT_SYNC_EMPTY_SNAPSHOT_REJECTED`, если клиент пытается заменить непустой снимок пустым; и `409 FLIGHT_SYNC_SUSPICIOUS_COUNT_DROP` при внезапном сокращении более 50% (если ранее было >=10 рейсов). Старый снимок не меняется. Для законного массового удаления нужна отдельная административная операция с явным подтверждением — эта версия намеренно не добавляет возможность слепой очистки.
- При повреждённом `snapshot_json` Worker отдаёт `503 FLIGHT_SYNC_SNAPSHOT_CORRUPT`, **а не `ok: true` с `flights: []`**.
- `flight_count` теперь вычисляется из действительного массива `flights[]`, включая legacy feed и статус администратора; `sync_state` различает `ready`, `empty`, `not_synchronized`.
- Старая постоянная HTML-ссылка сохраняется. Добавлен прямой машинный JSON `<stable-id>.json` (а также `?format=json`), ссылка на него видна на HTML-странице и копируется/шарится из приложения. Формат данных совместим: ранее существовавшие поля не удалены.
- Public GET по-прежнему read-only, без логина; административное сохранение по-прежнему требует авторизации. Ни один рейс и бронирование не изменялись этим патчем.

## Установка через GitHub

1. Загрузить архив `iumrah-business-flight-feed-recovery-20261015.zip` в **корень** репозитория `lattice-mobile-main` (не распаковывая). Workflow `.github/workflows/apply-zip.yml` подхватывает файлы из ZIP и коммитит изменения на `main`.
2. В Actions запустить вручную **Deploy iumrah Hotels Cloud**, дождаться зелёного результата. Новых миграций D1 не требуется. **Без деплоя Worker новая серверная защита не заработает.**
3. Для автоматического исправления снимка установить собранную новую версию **iumrah Business** (iOS/macOS), открыть «Авиабилеты → Опубликованные» и дождаться завершения синхронизации. При необходимости нажать «Синхронизировать». Клиент загрузит список с сервера и перезапишет *пустой* снимок фактическими активными рейсами.
4. Проверить в приложении «В Business: N · Feed: N». Открыть `https://iumrah.app/flights-feed/<stable-id>.json?fresh=<timestamp>`, удостовериться, что `flights.length == flight_count == N`, `sync_state == ready`, `updated_at` свежее. Старую HTML-ссылку менять не требуется.

## Пределы гарантии

- Пустой feed **не восстанавливается только деплоем Worker**. Так как Package Engine и снимок хранятся отдельно, нужно хотя бы одно успешное обновление снимка из нового клиента (пункт 3).
- Новое сокращение >50% требует отдельного подтверждённого механизма, иначе Worker's 409 сохраняет прежний снимок. Это намеренная защита от потери данных. Нужно устранять устаревшие рейсы в основном каталоге штатной бизнес-логикой; read-only GET ничего не удаляет.
- HTML/JSON маршрут может быть корректно доступен в Safari, но **ограничения инструмента веб-чтения ChatGPT (например, DisabledError) или DNS не устраняются изменением серверного кода**. Прямой JSON делает ответ понятнее для внешних клиентов, но не гарантирует доступ конкретного внешнего инструмента.
- Полная Xcode/TestFlight компиляция не проводилась: среда Linux без Apple SDK; Swift-файлы прошли `swiftc -frontend -parse`.
